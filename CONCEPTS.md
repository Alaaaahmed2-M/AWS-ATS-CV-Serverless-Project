# 🧠 Concepts, Decisions & Real Challenges

This document covers *why* the architecture looks the way it does, and the real problems hit during implementation — not just the happy path.

---

## Why this architecture?

A single EC2 instance running Flask is easy to demo, but it's a single point of failure and it's directly exposed to the internet. The goal of this project was to build something closer to a real production pattern:

- **Two EC2 instances across two Availability Zones**, so a single AZ failure doesn't take the app down
- **An Application Load Balancer in front of them**, so the EC2 instances are never contacted directly by users — only by the ALB
- **Serverless Lambda functions behind API Gateway** for the actual business logic (CV generation, JD analysis), so that part of the system scales automatically and has no servers to patch or manage
- **S3 + DynamoDB** as the persistence layer, chosen because neither needs to be provisioned or sized in advance

---

## Security decisions

### Security Group chaining
Instead of allowing `0.0.0.0/0` on port 80 directly on the EC2 security group, the EC2 security group's inbound HTTP rule references the **ALB's security group** as the source, not an IP range. This means:
- Requests must pass through the ALB
- Even if someone finds the EC2 instance's public IP, they can't reach port 80 on it directly

### Least-privilege IAM
The Lambda execution role's policy is scoped to the exact S3 bucket ARN and the exact DynamoDB table ARN — not `"Resource": "*"`. This limits the blast radius if the Lambda's credentials were ever compromised.

### S3 not public
The bucket keeps default Block Public Access settings. CV downloads work through **presigned URLs** generated by the Lambda function, which expire after a set time — the objects themselves are never public.

## Real challenges faced during implementation

Below are actual problems encountered while building this, along with the root cause and fix — not a cleaned-up version of events.

### 1. `Permission denied` when creating `app.py` on EC2
**Symptom:** `bash: app.py: Permission denied` when running `cat > app.py`.

**Root cause:** The EC2 `UserData` script ran `mkdir -p /home/ec2-user/ats-app/templates` as `root` during boot, so the directory ended up owned by `root:root`. The `ec2-user` session (used via EC2 Instance Connect) had no write permission inside it.

**Fix:** Use `sudo` when writing the file, e.g. `sudo bash -c 'cat > /home/ec2-user/ats-app/app.py << "EOF" ... EOF'`.

### 2. Multi-line heredocs getting corrupted in the browser terminal
**Symptom:** Pasting a large multi-line Python/HTML file into the EC2 Instance Connect browser terminal produced scrambled, interleaved output — lines got merged or duplicated mid-paste, and `__name__` silently became `name` in the pasted code.

**Root cause:** The browser-based terminal doesn't reliably support *bracketed paste mode*, so a large paste with many newlines can race with the shell's line-by-line echo/processing.

**Fix:** Encode the file content as a single-line **base64** string locally, then decode it server-side in one shot:
```bash
echo "<base64 content>" | base64 -d | sudo tee /home/ec2-user/ats-app/templates/index.html > /dev/null
```
A single line has no newlines to race against, which eliminated the corruption entirely.

### 3. `Failed to enable unit: Unit file ats-app.service does not exist`
**Symptom:** `systemctl enable ats-app` failed.

**Root cause:** Skipped a step — moved straight from creating `app.py` to `daemon-reload`/`enable` without ever writing `/etc/systemd/system/ats-app.service`.

**Fix:** Always verify with `sudo systemctl status ats-app` after each step, and confirm the unit file exists with `ls -la /etc/systemd/system/ats-app.service` before enabling it.

### 4. `500 Internal Server Error` on the homepage, but `/health` worked fine
**Symptom:** The ALB reported both targets as **healthy** (the `/health` route returned 200), but loading the actual homepage `/` failed with a generic 500 error.

**Root cause:** `render_template("index.html")` was called, but the file `templates/index.html` didn't exist yet on the instance — only `app.py` had been deployed. Flask/Jinja2 raised a `TemplateNotFound` exception, but the generic error page didn't say so.

**Diagnosis:** `sudo journalctl -u ats-app -n 30 --no-pager` showed the real traceback pointing at `jinja2.exceptions.TemplateNotFound`.

**Fix:** Deploy `templates/index.html` (same base64 technique as above) to **both** EC2 instances, then `sudo systemctl restart ats-app`.

### 5. SSH / EC2 Instance Connect intermittently refusing to connect
**Symptom:** `Failed to connect to your instance — Error establishing SSH connection. Try again later.`

**Root cause:** The security group's SSH rule was scoped to "My IP", but the IP EC2 Instance Connect actually originates traffic from (an AWS-managed range) doesn't always match the browser's own public IP as seen by the console at rule-creation time — especially behind mobile networks or NAT with a frequently-changing IP.

**Fix (lab environment):** Temporarily widened the SSH rule to `0.0.0.0/0` to unblock the session. For a real deployment, the correct fix is to allow the [documented EC2 Instance Connect IP ranges](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-instance-connect-set-up.html) for the target region instead of a blanket rule.

## Key takeaway

Understanding what each AWS service does in isolation is table stakes. The actual skill this project exercised was:
- Designing how services **connect** to each other (ALB → EC2 → API Gateway → Lambda → S3/DynamoDB)
- Reasoning about **security boundaries** between them (who can talk to whom, and why)
- **Debugging from evidence** (`journalctl`, `systemctl status`, target group health checks) instead of guessing when something breaks
